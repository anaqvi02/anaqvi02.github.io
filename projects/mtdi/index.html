ORIGIN STORY

Why it exists.

The short version: I ran a Minecraft server on my home lab, wanted strace on macOS, and found DTrace's flaming garbage fire instead, so I decided to fix it. The first pass was mtrace, a small syscall tracer. Then I realized tracing could become full instrumentation, and mtrace grew into mtdi. Everything since has been questions about inline hooks on arm64, safety, and speed, and the answers are the engine on this page.

HOW IT WORKS

The Engine.

It gets into a process two ways: at launch via DYLD_INSERT_LIBRARIES, or by attaching to a running process with task_for_pid() and a remote thread, which first has to be booted into a real pthread because a raw mach thread has no TLS and crashes dyld4. Once inside, hooks are inline detours: the trampoline layer disassembles the target's prologue, relocates it out of the way, patches in a jump to the probe wrapper, and thunks back so the original code continues untouched. A swap path can replace open() wholesale, and -l loads any pre-built dylib in any language.

HOW IT WORKS

Safe Probes & Output.

In -s mode you write a small Rust probe that registers hooks by symbol. The engine AST-verifies it against a zero-panic policy, compiles it with panic=abort, injects it, and gives the probe a safe context that can read and mutate args x0–x7, spoof return values, and block calls. Captured events land in a lock-free ring of aligned slots and stream out as plain text, NDJSON, or Elastic Common Schema, with an MCP server on the side for AI agents.

The numbers, measured on Apple M3: ~1.6 ns per fast-path call, ~15 ns per full-context hook, which is the 10–100× gap over Frida and the whole reason the project exists.
